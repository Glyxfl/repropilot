# ReproPilot 产品设计

## 一句话定位

面向刚进入课题组的研究生与承接重复分析任务的生信同学，把受限的两组 bulk RNA-seq 需求，自动交付为有计算依据、方法说明和复现脚本的结果包。

这是未经真实访谈验证的产品假设。项目作者的生信背景用于发现机会，不等同于已有用户调研、实验室合作或商业需求证明。

## 问题和场景

典型假设场景：实验同学在聊天中提出“处理组和对照组做差异，出火山图和 PCA”；分析同学确认方向与协变量、整理脚本、等计算、导图、解释结果、整理交付。已有统计工具很成熟，但分析意图、方法确认和最终交付之间仍有重复操作。

目标用户不是需要任意分析的资深生信专家，也不是希望完全绕开研究判断的人。第一版选择熟悉 RNA-seq 基础、需要明确结果与复现记录的研究生。

## 要完成的任务

“当我已有原始基因计数、想比较两个已知分组时，帮我把明确的方法执行成一组可检查的产物，让我把时间用于判断实验和结果。”

## 最小价值闭环

需求输入 → 结构化方法 → 人工确认 → 分析执行 → 结果验收 → 下载与回放。

每一环都有一个可观察的完成条件：方案满足参数契约；确认对应冻结方案哈希；统计产生有效结果；图像可读取；交付物存在且非空；统计回放数值在容差内一致。

## 关键产品决策

| 选择 | 原因 | 代价 |
| --- | --- | --- |
| 固定真实公开数据集 | 降低冷启动与数据授权门槛，便于验证端到端闭环 | 暂时不覆盖真实实验室输入 |
| 确认方案后执行 | 方向、协变量和阈值影响结论，应由研究者承担判断 | 多一次确认操作 |
| 模型仅提出固定参数 | 提高可测试性，避免把“代码能运行”误当“统计方法正确” | 无法覆盖开放式科研任务 |
| 报告从计算产物生成 | 减少无法追溯的解释；无需模型润色也可交付 | 第一版不生成机制解释 |
| 支持离线规划 | 招聘方无需购买密钥即可验证真正的计算链路 | 不将离线规划称为 LLM 能力 |
| 检查点恢复 | 下游图表失败无需重复已验证的统计拟合 | 检查点和哈希需要维护 |

## 创新点的合理表述

不是提出新的差异表达算法，而是组合出一个面向交付的研究工作流：**参数契约约束 Agent、方法确认门、工具级验收、检查点恢复、带指纹的科研交付包**。这是应用与交互上的创新，不能声称领域首创。

## 指标设计：目标与测量方法

目前没有真实用户指标，以下是待验证的指标定义，不能写成已达成业绩。

| 指标 | 测量 |
| --- | --- |
| 有效交付率 | 有完整且验收通过的产物 / 已确认且处于支持范围的任务 |
| 首次有效交付时间 | 从确认到 ZIP 验收通过，区分冷启动与热启动 |
| 人工干预次数 | 从明确需求到有效交付，研究者必须处理的非确认错误次数 |
| 方案方向正确率 | 盲评任务中，与研究者标注的 treatment/reference 是否一致 |
| 错误执行率 | 方法不适用或请求超范围，但仍执行并声称成功的比例 |
| 回放一致性 | 同环境对照结果，LFC / padj 误差在预设容差内的比例 |
| 恢复代价 | 下游失败后的重复计算量、重试时延与恢复成功率 |

## 两周真实验证计划

1. 找 3–5 位同门，询问最近一次 RNA-seq 分析的真实过程和交付要求。先观察工作，不推销工具。
2. 获得许可后使用非敏感公开数据做同任务对照，记录人工流程实际耗时、交付项和失败点。
3. 请其中两位使用 ReproPilot 完成相同任务，记录操作与误解，不预先讲解页面。
4. 与现有脚本或人工 notebook 比较方法一致性、交付完整性、重复运行成本。
5. 根据证据决定下一步：若输入接入是主要阻力再做上传；若多任务执行是阻力再接调度系统。

没有招到试用者前，将状态写为“个人项目 / 公开数据验证”，不写“服务课题组”。

## 后续范围与优先级

P0：真实模型标注评测集、真实试用、与 R DESeq2 的方法回归基线。

P1：经授权的用户数据输入、运行隔离与配额、取消任务、持久队列、用户身份。

P2：基因注释与有来源的富集分析、HPC/Nextflow 适配器、实验室可配置工作流。

是否实施以上能力应由验证结果决定，当前仓库不把它们展示为已完成功能。
